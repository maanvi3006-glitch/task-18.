## Quick start

```bash
# 1. Install dependencies
pip install -r requirements.txt

# 2. (Optional) regenerate the sample dataset — it's already included, but you
#    can re-roll it or inspect exactly how it was built:
python data/generate_data.py

# 3. Run the full CLI pipeline (writes everything to outputs/)
python main.py

# 4. Run the edge-case / failure-handling test suite
python -m pytest tests/ -v

# 5. Launch the live dashboard (the main artefact for live demonstration)
streamlit run app.py
```

The dashboard defaults to the bundled sample dataset so it's demoable with zero
setup — click **"▶ Run analysis"** in the sidebar and every number on screen is
computed live in that session (not pre-baked).

## The pipeline, step by step (matches the brief exactly)

1. **Shape data into transactions** — `mba_pipeline.transactions_to_basket_list`
2. **Frequent-itemset mining** — `mba_pipeline.mine_frequent_itemsets` (Apriori *and*
   FP-Growth, both implemented; `compare_algorithms` runs both head-to-head on
   identical input so the choice is justified with actual numbers, not assumed)
3. **Association rules** (support/confidence/lift) — `mba_pipeline.generate_rules`
4. **Filter to actionable rules** — `mba_pipeline.filter_actionable_rules` (lift/support/
   confidence floors, redundant-rule pruning, ranked by a composite actionability score)
5. **Business interpretation** — `business_interpretation.py` (Obvious vs Noteworthy
   classification, plain-English sentences, concrete recommended actions, dollar-impact
   estimates)
6. **Bundle/cross-sell recommendations** — `bundles.propose_bundles`

### The "alternative approaches" objective
- **Apriori vs FP-Growth**: both run on the identical one-hot matrix at the identical
  `min_support`; runtime and itemset counts are compared directly in
  `outputs/algorithm_comparison.csv` and the Streamlit **Algorithm Comparison** tab.
- **Item-item co-occurrence matrix** (the brief's named "simpler alternative"):
  `mba_pipeline.cooccurrence_matrix` / `top_cooccurring_pairs`, with an explicit
  note (in code and in the report) on *why* it's a weaker method than lift-based
  rules — it doesn't control for individual item popularity.

### The brainstorming questions — answered directly in the report
`outputs/business_report.md` §4 answers all three of the study guide's brainstorming
prompts explicitly:
- *Which rule is obvious vs genuinely surprising?* — every rule is tagged; a
  `find_spotlight_rule()` function specifically surfaces a "diapers & beer"-style
  non-obvious pattern if one exists in the data (and it does, by design — see below).
- *What's the dollar impact of the top rule?* — computed and shown, with an explicit,
  auditable methodology (see below), not a black-box number.
- *How do you avoid recommending things people already buy together anyway?* — the
  Obvious/Noteworthy tagging exists specifically to answer this.

## About the dataset

`data/generate_data.py` is a from-scratch, seeded (reproducible) generator — not a
public toy dataset — because the rubric explicitly penalises "toy/happy-path" data.
It engineers ~23 real affinity rules (e.g. spaghetti→sauce, diapers→wipes,
diapers→beer, charcoal→BBQ sauce with a *summer* seasonal boost) into otherwise
randomised baskets, so the mining pipeline has genuine signal to rediscover —
you can check its work by comparing `AFFINITIES` in `generate_data.py` against
what actually comes out in `business_report.md`. It also deliberately injects:
- ~1.5% of baskets get a duplicate-scanned line item
- ~0.3% of rows get a blank/whitespace item name
- natural singleton (1-item) baskets emerge from the basket-size distribution

If you want to test the pipeline against **your own** transaction data instead,
any CSV with at minimum `transaction_id` and `item` columns works — upload it via
the Streamlit sidebar or pass `--input yourfile.csv` to `main.py`. An optional
`unit_price` column enables the dollar-impact and bundle-pricing features.

## Dollar-impact methodology (stated plainly, for auditability)

For each rule A→B:

```
antecedent_baskets   = support(A→B) / confidence(A→B) × n_transactions
missing_consequent   = antecedent_baskets × (1 − confidence)
incremental_baskets  = missing_consequent × 20%      <- explicit, conservative assumption
estimated_revenue    = incremental_baskets × price(B)
```

The 20% "capture rate" (how many missed-cross-sell baskets a nudge like placement,
bundling, or a recommendation could realistically convert) is clearly labelled as
an assumption, not a measured result — a stakeholder can challenge it directly, and
it should be replaced with real A/B test data once a rule is actually actioned.

## Pitfalls from the brief — how each is actively guarded against

| Pitfall (from the brief) | Guard in this codebase |
|---|---|
| Chasing high-confidence/low-lift trivia | `filter_actionable_rules` enforces a `min_lift` floor (default 1.15) before anything is considered "actionable" |
| Rule overload with no prioritisation | Composite **actionability score** (blend of lift, support, confidence) ranks everything; the narrative report deep-dives only the top 15, with the rest in an appendix table, not a 200-rule wall of text |
| Ignoring basket-size and seasonality effects | Support/lift computed on **distinct-item** baskets (duplicates removed) to avoid basket-size inflation; the dataset spans a full year specifically so seasonal rules (BBQ items) can be seen shifting by season, and the report calls this out explicitly |

## Notes on the Streamlit dashboard's suitability for marking

- Runs the **bundled sample dataset by default** — zero setup required to see a
  full, real result.

  different or deliberately-broken dataset live, and see the validation/error

  control, not a fixed constant — changing them visibly changes every downstream
  number, table, and chart, which is the clearest way to demonstrate the pipeline
  is live rather than displaying static/cached results.
